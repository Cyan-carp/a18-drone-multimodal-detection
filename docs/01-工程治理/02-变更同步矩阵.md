# 变更同步矩阵

用于回答"改完之后还欠哪几笔"。矩阵给最小集，避免把一次修复扩散成全库重写，也避免漏掉状态回写。

## 1. 最小同步集

| 变更类型 | 必改 | 条件触发 | 明确不要做 |
| --- | --- | --- | --- |
| 普通 Bug 修复（行为不变） | 对应源码；必要时 `shared-memory` 记一条验证结论 | 接口或命令变了 → 改 [接口契约](../02-方案与契约/02-前后端接口契约.md) 与脚本 | 不改状态页的阶段性结论，不重写方案页 |
| 新增/变更接口、参数、错误码 | [接口契约](../02-方案与契约/02-前后端接口契约.md)、对应 Controller、前端 `lib/api.ts` | 影响前端调用 → 同批改调用处 | 不复制第二份字段表到计划页 |
| 能力或阶段推进 | [当前系统状态](../00-当前系统状态.md) + [验收清单](../03-开发计划与验收/03-验收清单.md) 状态列 | 有实测证据 → 记入证据列 | 不把"能编译"写成"已验收" |
| 模拟引擎参数或算法变化 | [重建方案](../02-方案与契约/01-演示平台重建方案.md) §模拟引擎 | 影响对外数值 → 更新验收基线 | 不改 `config/reference/` 的历史快照 |
| 新增/替换参考数据 | `config/reference/README.md` 登记来源 | 影响模拟输出 → 更新状态页摘要 | 不覆盖已有快照，用新文件名 |
| 新增启动/构建脚本 | 脚本本身 + 根 [README](../../README.md) 命令入口 | 影响依赖安装 → 状态页环境节 | 不在文档里维护第二套命令 |
| 目录移动或改名 | 全部入链、[导航](../00-导航·项目文档.md)、分区索引 | 有历史记录 → [基线复制清单](../09-历史与证据/02-基线复制清单.md) 追加映射 | 不留旧路径残留，不建同名正文 |
| 治理规则变更 | 本分区两页 | 影响检查器 → `tools/governance-config.json` | 不保留新旧两种写法 |

## 2. 本仓库不适用的场景

- **生产发布与回退**：本仓库只产出本地演示，无服务器、无镜像、无生产指针，`powersystem-release-governance` 的方法暂不适用。若未来需要部署，必须先补"发布与恢复"规范再执行。
- **阶段交接四件套**：项目规模不够，收敛为 [验收清单](../03-开发计划与验收/03-验收清单.md) + 状态页两件。若后续增加人员协作，再引入独立问题记录与交接页。

## 3. 四种变更的走查要求

每次改变治理结构后，至少拿下面四类真实变更走一遍，并记录"应改 / 不需改 / 证据"：

| 场景 | 期望行为 |
| --- | --- |
| 单次修复模拟引擎的召回参数 | 只改引擎与方案页 §算法；状态页不动；验收清单记录新数值 |
| 新增一个接口（如批量重跑） | 契约、Controller、前端调用、验收清单条目同批出现 |
| 阶段从"未开始"到"已实现" | 状态页能力行、验收清单状态列、`shared-memory` 验证结论三处一致 |
| 把 `legacy/python` 改名 | 导航、legacy README、基线清单映射与全库引用同批更新 |

## 4. 收尾检查清单

1. 该改的文件是否同批改完（按第 1 节）？
2. 是否出现了同一事实的第二份正文？
3. 状态值是否有实际证据支撑？
4. `python tools/check_docs.py --root . --config tools/governance-config.json` 是否通过？
5. 未执行项是否被如实标注，而不是留空？
